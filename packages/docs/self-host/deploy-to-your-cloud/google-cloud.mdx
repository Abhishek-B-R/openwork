OpenWork supports two Google Cloud deployment shapes. Use GKE Autopilot and Helm when you need the full chart surface. Use the Cloud Run starter for a serverless Den Web and Den API deployment with a separate migration job.

## Choose a deployment target

Choose GKE when you need Helm hooks, pod-level customization, custom CA mounts, installer artifact volumes, or the optional OpenWork Gateway. Choose Cloud Run when Den Web and Den API fit the request-driven service model and you prefer managed autoscaling without a Kubernetes cluster.

## What Google Cloud manages

- GKE control plane and Autopilot compute lifecycle
- VPC networking, Cloud Load Balancing, firewall rules, and IAM
- Cloud SQL for MySQL, encryption, backups, and failover
- Cloud DNS and Google-managed certificates when you use those services

The OpenWork chart manages Deployments, Services, ConfigMaps, Secret references, probes, the Ingress, and the database migration Job. GKE `BackendConfig` and `ManagedCertificate` resources are applied alongside the chart.

## GKE checklist

1. Enable the Kubernetes Engine, Compute Engine, Cloud SQL Admin, and Service Networking APIs.
2. Create a regional GKE Autopilot cluster and install `gke-gcloud-auth-plugin` if your Cloud SDK does not include it.
3. Configure private services access and create Cloud SQL for MySQL with a private IP.
4. Reserve a global IPv4 address and create the GKE health-check and certificate resources.
5. Store `DATABASE_URL`, `BETTER_AUTH_SECRET`, and `DEN_DB_ENCRYPTION_KEY` in a Kubernetes Secret.
6. Start from the chart's `values.gcp-ingress.yaml` example, install the chart, and verify migrations and readiness.
7. Point both hostnames at the reserved address and wait for the managed certificate to become active.

For exact GKE commands, values, health checks, migration troubleshooting, verification, and cleanup, follow the [GKE operator runbook](https://github.com/different-ai/openwork/blob/dev/docs/gcp-gke-helm.md).

## Cloud Run checklist

1. Enable Cloud Run, Artifact Registry, Cloud SQL Admin, and Secret Manager APIs.
2. Mirror the versioned Den API and Den Web images into Artifact Registry.
3. Create Cloud SQL for MySQL and store independent application secrets in Secret Manager.
4. Render the starter service and job manifests from `packaging/cloud-run`.
5. Execute the migration job before deploying the API and Web revisions.
6. Verify all four health and readiness endpoints before opening setup.

Follow the [Cloud Run operator runbook](https://github.com/different-ai/openwork/blob/dev/docs/gcp-cloud-run.md) for the manifests, exact commands, migration ordering, verification, and upgrade notes.

## Cloud Run with Terraform (draft)

A draft Terraform module deploys the Cloud Run path in one `terraform apply`: Den API and Den web as Cloud Run services, Cloud SQL for MySQL 8.4 reached through the Cloud SQL connector, secrets in Secret Manager, and the migration job, which runs during the apply before Den API is updated. It pulls the published images through an Artifact Registry remote repository that proxies `ghcr.io`, so you do not mirror images by hand.

<Warning>
  The module is an early draft, and inputs may change. Pin it to a commit, and open an issue or pull request for anything that fails in your environment.
</Warning>

You don't need a domain to start: by default the services use their HTTPS `run.app` URLs. Set `domain_name` to put both hostnames (the web host and `api.` plus the web host) behind a global external HTTPS load balancer with a Google-managed certificate. You can reuse an existing VPC (Direct VPC egress), an existing database or Cloud SQL instance, a service account, certificates, and a reserved IP address. Email is optional for setup and sign-in, but member invites and password reset need SMTP or Resend.

The account that runs `terraform apply` must be able to set IAM policies: the module grants its service account Cloud SQL access and access to each secret, and lets browsers reach the services without Google sign-in (Den does its own sign-in). Project Editor alone is not enough; add Project IAM Admin and Cloud Run Admin, or let your platform team grant `roles/cloudsql.client` and `roles/secretmanager.secretAccessor` and set `grant_iam_roles = false`.

**What was tested.** The module was applied with its defaults (Secret Manager, IAM grants, public access) in a Google Cloud test project, using `examples/complete` and release 0.18.58:

- the migration job ran during the apply on an empty Cloud SQL for MySQL 8.4 database;
- Den API and Den web answered over HTTPS on their `run.app` URLs, and both readiness checks passed;
- in a browser, the one-time setup page on Den web created the first administrator, and a new browser session signed in to the dashboard;
- an isolated OpenWork desktop app signed in to the deployment, and the deployment's API accepted its session as the administrator.

Earlier runs also checked Direct VPC egress into an existing VPC, and the load balancer with a custom hostname. In that run, the Google-managed certificate became active for both hostnames in about 7 minutes, each hostname reached the right service, and HTTP redirected to HTTPS. Not yet tested: an existing database, several Den API instances, email delivery, and upgrades between releases. OpenWork Web, the Slack assistant, headless Automations and Workbot are not in this module yet; use the ECS module or the Helm chart for those.

See the [module README](https://github.com/different-ai/openwork/tree/dev/infra/terraform/modules/openwork-gcp-cloud-run) for inputs, a complete example, and cost notes.
